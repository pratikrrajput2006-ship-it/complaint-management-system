# Complaint Management System (CMS)

A web-based **Complaint Management System (CMS)** for an educational institution. The system is being developed as a role-based web application using HTML, CSS, JavaScript, Node.js, Express, and MySQL.

The project is being developed incrementally: backend functionality is implemented and tested first, then the corresponding frontend module is built and connected to the available APIs.

---

## 1. Project Objective

The main objective of the CMS is to replace an unstructured/manual complaint process with a centralized system that can:

- Accept complaints from Students and Staff
- Route complaints to the responsible Department
- Allow Admin to control departments, categories, assignments, and system configuration
- Assign complaints to Staff
- Track complaint status and history
- Handle escalation to Higher Authority (HA)
- Preserve important administrative and HA history
- Record final resolutions
- Collect feedback
- Provide secure authentication and role-based authorization

---

## 2. Main Users and Responsibilities

### Student

A regular user who can register and use the complaint system.

**ID format:** `STU###`

Main functions:

- Register
- Login
- View dashboard
- Submit complaints
- View and track own complaints
- View resolution
- Reopen complaints where permitted
- Give feedback
- Receive notifications

### Staff

A regular user who can submit personal complaints and can also handle complaints assigned by Admin.

**ID format:** `STF###`

Main functions:

- Register
- Login
- View dashboard
- Submit own complaint
- View assigned complaints
- Accept/handle assigned complaints
- Update status
- Add remarks
- Resolve complaints
- Escalate complaints to Higher Authority when required

### Admin

A controlled/privileged account responsible for system management.

**ID format:** `ADM###`

Admin is **not a public registration role**.

Main functions:

- Login
- View Admin dashboard
- Manage departments
- Manage categories
- Verify Staff for HA assignment
- Assign and remove HA responsibility
- View HA history
- Manage users and controlled system functions as implemented
- Monitor complaints
- Manage complaint assignments
- View reports/analytics in the later dashboard stage

Admin is a **system manager/monitoring role**, not the normal complaint-resolving role.

### Higher Authority (HA)

Higher Authority is **not a separate user identity or separate login account in the current design**.

HA is an additional responsibility assigned to an existing Staff account by Admin.

- No separate HA ID
- No separate HA login
- Existing Staff ID remains permanent
- Current HA state is stored through the Staff record
- Important HA assignment/removal history is preserved in `HA_HISTORY`

## 3. Account and ID Model

The application uses readable IDs generated by backend/database logic.

| Entity / Role | Format | Example |
|---|---|---|
| Student | `STU###` | `STU001` |
| Staff | `STF###` | `STF001` |
| Admin | `ADM###` | `ADM001` |
| Department | `DEP###` | `DEP001` |
| Category | `CAT###` | `CAT001` |
| Complaint | `CMP###` | `CMP001` |
| Assignment | `ASN###` | `ASN001` |
| Tracker | `TRK###` | `TRK001` |
| Notification | `NOT###` | `NOT001` |
| Feedback | `FDB###` | `FDB001` |

There is **no HA sequence** because HA is an additional authority on an existing Staff account.

`ID_SEQUENCE.next_number` represents the next available number for the configured role/entity sequence and is accessed transaction-safely when IDs are generated.

## 4. Login and Authentication

One common login page is used for the system.

```text
Email + Password
      ↓
Common Login API
      ↓
USER lookup
      ↓
Password verification
      ↓
Read role
      ↓
JWT token generated
      ↓
Role-based dashboard
```

Current backend login response includes:

- `user_id`
- `name`
- `role`
- `token`

The frontend stores the token and basic user information in `localStorage`.

Protected API requests use:

```http
Authorization: Bearer <token>
```

Backend authorization returns the appropriate response for protected routes:

- `401 Unauthorized` for missing/invalid authentication
- `403 Forbidden` for an authenticated user without the required role

## 8. Database Design

The final current design separates a user's own department from the department responsible for handling a complaint.

### USER

Common account information:

```text
PK  user_id
    name
    email
    password_hash
    role
    phone
    status
    created_at
```

### ADMIN

```text
PK/FK admin_id → USER.user_id
    employee_no
    designation
```

### STAFF

```text
PK/FK staff_id → USER.user_id
    employee_no
    department_id
    designation
    ha_status
```

`ha_status` represents the current HA state of the Staff member, such as `NONE` or `ACTIVE`.

### STUDENT

```text
PK/FK student_id → USER.user_id
    prn
    department_id
    course
    year
    address
```

### DEPARTMENT

```text
PK  department_id
    department_name
    status
    created_at
```

Admin manages Departments. Departments are activated/deactivated rather than deleted.

### CATEGORY

Current final category design:

```text
PK  category_id
    category_name
    department_id
    status
    created_at
```

`department_id` identifies the department responsible for handling that normal complaint category.

`routing_type` is **not part of the final category design**.

### HA_HISTORY

Preserves important HA assignment history:

```text
PK  history_id
FK  staff_id
FK  department_id
FK  assigned_by → ADMIN.admin_id
    assigned_at
    ended_at
    status
    remark
```

### ID_SEQUENCE

Stores the next available number for configured ID sequences.

```text
PK  role
    next_number
```

The sequence is read with a transaction-safe lock when an ID is generated.

## 9.1 Complaint-Side Final Design

The complaint module is the next major functional block after the current Admin frontend work.

### COMPLAINT

```text
PK  complaint_id
FK  submitted_by → USER.user_id
FK  category_id
FK  department_id
    subject
    description
    attachment
    status
    priority
    created_at
    updated_at
    resolved_at
    resolution
```

The complaint stores both `category_id` and `department_id` so that the responsible department at the time of complaint creation remains historically meaningful even if a category's routing configuration is later changed.

### ASSIGNMENT

Stores Admin-to-Staff complaint assignment history.

```text
PK  assignment_id
FK  complaint_id
FK  staff_id
FK  assigned_by → ADMIN.admin_id
    assigned_at
    assignment_status
    remark
```

### COMPLAINT_TRACKER

Stores chronological complaint status/history information.

```text
PK  tracker_id
FK  complaint_id
FK  updated_by → USER.user_id
    status
    remark
    updated_at
```

### NOTIFICATION

```text
PK  notification_id
FK  user_id
FK  complaint_id
    title
    message
    notification_type
    is_read
    created_at
```

### FEEDBACK

```text
PK  feedback_id
FK  complaint_id
FK  user_id
    rating
    comment
    created_at
```

## 10. Department Logic

The system distinguishes two different department meanings.

### User's Department

The department to which a Student or Staff member belongs.

Example:

```text
Staff → Electrical Engineering
```

### Complaint Responsible Department

The department responsible for handling a particular complaint.

Example:

```text
Student Department      = Computer Science and Engineering
Complaint Category      = Hostel
Responsible Department  = Hostel / responsible service department
```

A user's own department therefore does **not** automatically determine the destination of every complaint.

---

## 11. Higher Authority Logic

The current design uses **Department-Level HA**.

```text
Admin
  ↓
Verify existing Staff
  ↓
Select responsible Department
  ↓
Assign HA responsibility
  ↓
STAFF.ha_status = ACTIVE
  ↓
Save record in HA_HISTORY
```

Removal follows the reverse state change while preserving the historical record.

Important rules:

- HA is not a separate account
- No HA ID is generated
- The Staff ID remains unchanged
- A Staff member can have one active HA assignment at a time
- HA history is preserved for auditability
- Admin makes the final assignment decision

## 18. Security Practices

The project applies the following security practices:

- Passwords stored as bcrypt hashes
- Passwords never stored as plain text
- JWT-based authentication
- Backend role-based authorization
- Parameterized SQL queries
- Environment variables for database credentials and JWT secret
- `.env` excluded from Git
- Protected Admin operations verified on the backend
- Department/HA actions validated server-side
- Transactions used for multi-step ID/account operations
- Historical records preserved where required for auditability

Hiding a button in the frontend is **not** considered a security mechanism. Authorization is enforced by the backend.

---

## 19. MySQL Design Rules

- Use primary keys for major entities
- Use foreign keys for relationships
- Use readable generated IDs such as `STU001`, `STF001`, and `DEP001`
- Use `password_hash` instead of storing passwords directly
- Validate input before database writes
- Use parameterized queries
- Use transactions when multiple database changes must succeed together
- Store current complaint state separately from historical tracking data
- Preserve HA history
- Do not delete Departments; change their operational status instead
